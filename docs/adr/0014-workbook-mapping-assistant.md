# ADR 0014 — Mapping arbitrary budget CSVs: in-browser learned mapper, optional LLM assistant

- Status: proposed
- Date: 2026-10-11
- SPEC: §6.2 (FR-ING-015…018), §13.2, §19 (M8, M10)

## Context

Everyone lays out a budget differently: section header rows, pivoted months, merged columns,
notes in cells, several tables on one sheet, their own period words ("fortnightly", "pa"). The app
needs one standard inside (`BudgetLine`, `Asset`, `Goal`). Today a preset and alias matcher plus a
mapping wizard (ADR 0010) handles layouts close to the presets.

The question is whether a light ML model in the browser can do the structuring, or whether it needs
an LLM.

## Decision

Mapping a CSV is **schema matching**, not free-text generation. The output is a small, checkable
**mapping spec**: for each column, the field it fills and its parse rule; which rows are headers,
sections or totals; and the period vocabulary.

Every proposer, from rules to an LLM, emits the same mapping-spec JSON, validated against a JSON
Schema (`schemas/mapping-spec.schema.json`) by the in-house validator. Deterministic code then
applies the spec, and the user confirms it in the existing preview. **No proposer ever writes a
budget figure** (NFR-HON-002): values come only from the user's cells.

Three tiers, each used only when the one before is unsure:

1. **Rules** (exists): presets, header aliases, and value-type detection (dates, money, period
   codes).
2. **In-browser learned mapper** (M10):
   - A small model classifies each column and row role from features: header tokens (hashed
     n-grams), value statistics (share numeric or money-like, date patterns, distinct ratio, sums
     matching a totals row) and position.
   - It runs in ml-core: logistic regression or a small gradient-boosted tree, kilobytes in size.
   - It is trained offline on synthetic budgets in many layouts, generated by extending
     `src/synth` (the generator already knows the ground truth). Online, it learns from the user's
     own wizard corrections, kept locally.
   - Optional later: a small sentence-embedding model for header semantics. That needs an ADR
     under ADR 0007 (no third-party runtime code) because it means ONNX/WebGPU weights.
3. **LLM mapping assistant** (M8, optional, off by default):
   - Used for layouts the first two tiers can't resolve.
   - It receives the header rows and a few sampled rows, redacted under FR-API-003 (amounts
     bucketed), and returns a mapping spec through **structured outputs**: the Claude API's
     `output_config.format` with a JSON Schema, or a `strict: true` tool. OpenAI-compatible
     providers get a `json_schema` response format.
   - The response is validated again locally. Consent and logging follow FR-API-001…005.

## Why not an LLM only, or ML only

- **LLM only:** it would make an optional, networked, paid component mandatory for import. It would
  send budget data off the device for every file. And it isn't needed for most layouts.
- **ML only:** genuinely unusual layouts (several tables on one sheet, prose notes, pivoted years)
  are long-tail. A small classifier needs an escape hatch for them.

Most sheets are expected to stay on the device. The LLM is the opt-in fallback.

## Why not Zod

ADR 0007 rules out third-party runtime code. JSON Schema is what the structured-output APIs accept
anyway, and the app already has a validator.

## Consequences

- The mapping wizard gains "suggested by: rules / model / LLM" with a confidence per column. Every
  suggestion can be edited.
- An evaluation set of synthetic layouts gates the mapper in CI. The target is ≥ 95 % column
  accuracy on held-out layouts, the same pattern as FR-CLS-005.
